# 技术栈详解 —— 每项技术在桌宠项目中的实际作用

> 依据《灵梦桌宠二版》项目介绍所列技术栈逐项展开，全部内容对应项目真实代码与模块，可直接用于技术讲解与答辩追问。
> 逐项结构：**角色定位 → 具体做了什么 → 选型理由 → 一句话总结**

---

## 一、Tauri v2 —— 桌面壳与"总装车间"

**角色定位**：整个桌面应用的容器与粘合剂，本身不承载业务逻辑。

**具体做了什么**：
- 提供应用入口、窗口管理、系统托盘等桌面基础能力，Vue3 控制台跑在它的 WebView 里（生产环境前端资源内嵌进主程序 exe）；
- **进程管家**：启动时拉起打包在资源里的 Python 网关（`desktop-pet-gateway.exe`）并轮询 `/api/health` 健康检查，通过后才放行 UI；启动时注入 `DESKTOP_PET_CONFIG_DIR / DESKTOP_PET_DATA_DIR` 环境变量，把配置和数据导向用户目录（`%LOCALAPPDATA%`）——这是"升级不覆盖用户密钥"的前提；同时负责启动/关闭 Godot 渲染进程，实现崩溃隔离（Godot 挂了不影响控制台）；
- **安装载体**：通过 `tauri.conf.json` 的 resources 映射，把内嵌前端的 exe、PyInstaller 产出的 gateway 目录（含人脸模型）、Godot 桌宠资源总装成一个 MSI 安装包。

**选型理由**：对比 Electron 内存占用更小、体积更小，且 Rust 侧可直接做进程管理和文件操作。

**一句话**：Tauri 不干活，它负责让"Vue 控制台 + Python 网关 + Godot 渲染器"三个异构进程像一个应用。

---

## 二、Vite + Vue3 —— 控制台与调试中枢的前端

**角色定位**：桌宠的"驾驶舱"界面，所有能力的前端入口。

**具体做了什么**：
- 构建整套控制台 UI：对话、语音、身份、记忆、工具审批、RAG、资源调试等面板；
- 封装各能力的客户端模块（`src/agent`、`src/voice`、`src/identity`、`src/tools`、`src/memory`、`src/rag`），每个模块配 Vitest 单元测试；
- 语音侧前端工程：`AudioRecorder`（16kHz 采集）、`VoiceActivityDetector`（VAD 断句）、`WakeWordGate`（唤醒词门控）、`AudioLipSyncPlayer`（WebAudio 播放 + 口型能量计算）、`SpeechPlaybackCoordinator`（播放状态协调，防止 Agent/TTS 期间重复提交）；
- 调试历史存 localStorage，重启可查。

**选型理由**：CompositionType 响应式系统适合高频 WebSocket 状态更新；Vite 秒级热更新支撑多面板联调。

**一句话**：Vite+Vue3 把"看不见的后端能力"变成看得见、可操控、可排查的界面。

## 三、MiniMax TTS —— 桌宠的"嗓子"

**角色定位**：拟人化设计中"说"的部分，把智能体的文字回复合成为多音色语音。

**具体做了什么**：
- 经本地网关代理调用 MiniMax t2a_v2 接口，返回十六进制音频，前端 WebAudio 播放（HTMLAudio 兜底）；
- 多角色音色：中文傲娇/温柔/御姐、日语、英语等，与 Persona 人设联动（`personaVoices`）；
- **口型同步的数据源**：播放期间的音频能量实时计算，驱动桌宠口型在 closed / half-open / open 间切换，配合"说话"动作——这是"回答即演出"的下半场；
- 播放状态与链路状态机联动（TTS 期间防重复提交、失败不影响文本对话）。

**选型理由**：多语言音色质量好、接口稳定；经网关代理后 API Key 不下发前端。

**一句话**：MiniMax 让桌宠从"显示文字"变成"开口说话"，还顺手解决了口型从哪来的问题。

---

## 四、豆包 SAUC ASR —— 桌宠的"耳朵"

**角色定位**：拟人化设计中"听"的部分，实时流式语音转文字。

**具体做了什么**：
- WebSocket 全双工流式识别（SAUC 协议），16kHz/16-bit/单声道 PCM 分块上传，支持 partial（中间结果实时上屏）/ final（完整句提交智能体）双事件；
- 与前端 VAD 断句、唤醒词"小赤红"本地门控配合，实现连续对话；识别防重（重复 final 不重复提交 Agent）；
- 中 / 日 / 英三语均完成真实接口端到端验收；
- **链路隔离**：ASR 只负责转写，其文本/日志绝不能作为身份认证证据（与声纹/人脸认证严格分开）。

**选型理由**：流式低延迟（边说边识别）是"实时长对话"体验的关键，SAUC 协议分块直传无需等整句。

**一句话**：豆包 ASR 让对话从"你一句我一句打字"变成"随时开口、实时反馈"。

## 五、OpenCV（YuNet + SFace）—— 主人认证与权限大门

**角色定位**：身份验证模块，决定桌宠"对谁敞开全部能力"。

**具体做了什么**：
- **检测**：YuNet（`FaceDetectorYN`）负责人脸定位，置信度阈值 0.6、NMS 0.3——默认 0.9 在普通室内光照或侧脸下会漏检，因此下调；
- **特征**：SFace（`FaceRecognizerSF`）在检测框上 `alignCrop` 对齐，输出 128 维身份嵌入并做 L2 归一化。早期用 MediaPipe 478 个 3D 关键点做刚性归一化，实测同人与他人的相似度间隔仅 -0.0086，几何关键点不是身份嵌入，已整体替换；
- **注册**：≥3 张主人照片逐张"解码 → 检测 → 取最高分人脸 → 对齐 → 128 维嵌入"，写入本地 JSON 档案（`name + base64(float32×128) + feature_dim + feature_backend=sface`），**原始照片仅内存解码，不落盘**；验证：新图提特征后与档案内全部参考特征算余弦，取最高分，≥0.45 判定 `owner_verified`；
- **权限联动**：主人态解锁长期记忆读写与高权限工具（文件阅读、白名单应用控制等）；陌生人与低相似度一律回落 guest；完全离线运行，人脸数据不出本机；
- **可替换性**：统一收敛到 `FaceVerificationAdapter`（引擎可注入），因此"声纹→人脸""关键点→SFace"两次迁移时，`IdentityService` 的权限位、审计与接口契约均未改动。

**选型理由**：完全本地推理（数据不出机器）、CPU 实时、无需云端账号；SFace 是人脸识别专用嵌入，区分度远高于几何关键点；运行期只依赖 opencv-python，网关产物 236 MB，比 mediapipe 方案（370 MB+）更轻。

**一句话**：YuNet + SFace 是桌宠的"认人"能力，也是整个权限体系的开关。

## 六、SQLite —— 长期记忆与治理中枢（不止存记忆）

**角色定位**：本地嵌入式关系库，承载所有需要"确定性、可治理"的数据。

**具体做了什么**（实际用途比"存记忆"更宽）：
- **长期记忆**：候选—确认两段式——对话中模型最多提议 3 条记忆候选，用户在界面确认后才生效；敏感内容（密钥/卡号/证件号）入库前正则拦截；确认记忆以"事实背景、绝非指令"标记注入后续对话（默认最近 12 条）；owner 身份门控读写；
- **工具治理**：审批单（中风险操作 10 分钟内人工确认）+ 执行审计表（谁、何时、做了什么、结果如何）；
- **本地提醒**：一次性提醒持久化，到期只派发提醒事件，绝不触发命令。

**为什么用 SQLite 而不是 Milvus 存记忆**：记忆是"少量、精确、必须全量可靠注入、带状态机治理"的数据——需要事务（候选→确认流转）、需要一条不漏（向量召回是概率性的，漏一条"你叫什么"就是事故）、需要零部署（桌面应用带不动常驻向量服务）。向量库解决"大海捞针"，记忆的问题是"一根针都不能丢"。

**一句话**：SQLite 管"确定性与信任"——凡是需要精确、可审计、用户可控的数据都在它这里。

## 七、Milvus —— RAG 角色知识库

**角色定位**：桌宠的"参考书架"，语义检索的知识来源。

**具体做了什么**：
- 双集合设计：`character_knowledge`（角色设定/世界观）与 `user_documents`（用户上传文档），.txt/.md 上传后切块、向量化入库；
- 对话时按用户消息语义检索 top-3 片段，以 `[不可信参考资料]` 标记注入提示词（防知识库投毒/指令注入），回答携带 `sources` 来源标注（文件名 + 块序号）与 `rag_status` 状态；
- **降级设计**：Milvus 不可用不阻断聊天，仅标记 `unavailable`，知识库与记忆、聊天链路物理隔离，互不污染。

**选型理由**：角色设定和上传文档是非结构化文本，"按语义找相关内容"正是向量检索的主场；双集合隔离让角色知识与用户资料互不干扰。

**一句话**：Milvus 让桌宠"读过哪些书、说话有出处"，与 SQLite 的"记得你批准的事"分工明确、永不互通。

## 八、Godot 4.7 —— 桌宠的"身体"与动作引擎

**角色定位**：独立渲染进程，把智能体的决策变成看得见的动作表演。

**具体做了什么**：
- 透明无边框桌面窗口 + SpriteSheet 精灵图动画：按 manifest 描述切帧，驱动待机/聆听/思考/说话/不悦/害羞/打开应用等动作状态机；
- **文件协议解耦**：Tauri 侧把智能体输出的动作 ID、口型模式写入 `preview.json`，Godot 轮询读取执行——两侧零直接耦合，Godot 崩溃不影响主程序，缺资源自动回退占位动画；
- 口型随 TTS 音频能量实时开合（closed / half-open / open），与"说话"动作合成完整表演；
- 底部锚点稳定，动作切换不跳动，重启后状态可恢复。

**选型理由**：成熟 2D 动画状态机能力 + 独立进程天然隔离；用文件协议而非 IPC，调试和容错都更简单。

**一句话**：Godot 是桌宠的"身体"，preview.json 是大脑与身体之间的神经信号。

## 九、LangGraph —— 智能体工作流编排（已落地）

**角色定位**：把"上下文组装 → 规划 → 执行 → 后处理"组织成显式状态机，并为工具审批提供可暂停、可恢复的跨请求状态。

**落地形态**：代码位于 `backend/app/agent_workflow/`，四个文件分工明确——`state.py` 定义 `AgentWorkflowState` / `ToolApprovalState`，`nodes.py` 定义节点与条件边，`runner.py` 负责编译图、检查点与执行入口，`approval_graph.py` 是工具审批子图。

- **主对话图**：10 个节点（上下文组装、本地规划、执行受控工具、格式化工具回复、本地模拟应答、调用远程模型、提供方不可用、本地降级应答、显式报错、后处理），3 条条件边分别判断"是否命中确定性工具""远程是否产出结构化响应""失败是否允许降级"；
- **工具审批子图**：4 个节点，`interrupt()` 暂停等待人工决定，`Command(resume={"action": "approve" | "reject"})` 恢复；线程标识 `tool-approval:{call_id}`，当前只接管 `open_file`，其余工具仍走 `ControlledToolService` 原审批；
- **检查点**：默认 `InMemorySaver`（重启即清），设置 `LANGGRAPH_CHECKPOINT_ENABLED=true` 后写 SQLite（`AsyncSqliteSaver`）；主图线程为 `agent:{session_id}`；
- **双引擎**：`AgentService.respond` 按 `AGENT_WORKFLOW_ENGINE` 选择 `_respond_legacy` 或 `AgentWorkflowRunner.run`，两条路径共用同一批服务与 `AgentResponse` 契约，安全边界不因换引擎而改变；
- **为什么保留 legacy**：LangGraph 带来状态可见性与中断恢复能力，也带来依赖与调试成本；先双轨运行、验证稳定后再收敛，比一次性删旧链路更稳。

**一句话**：LangGraph 在这里不是"用了框架"，而是把原本隐含在 if/else 里的分支、降级与人工介入，变成可绘制、可检查点、可恢复的显式状态机。

## 十、技术栈协同总览：一次语音对话中谁在参与

```
你开口 → [Vue3 采集+唤醒词+VAD] → [豆包 ASR 流式转写]
      → [智能体编排(LangGraph 主图 / legacy 回退)]：
           读 [SQLite 长期记忆] + 检索 [Milvus 角色知识] + 明确指令直达 [受控工具]
           → 结构化输出(文本/情绪/动作/口型)
      → [MiniMax TTS 合成] → [Vue3 WebAudio 播放+口型能量]
      → [Godot 按 preview.json 表演] —— 全程 [Tauri] 守护进程与状态
      → 主人认证由 [OpenCV YuNet+SFace] 决定本次能开放多少能力
```

每一项技术各司其职、经本地网关解耦、可独立替换——这正是整个项目"链路可观测、服务可替换"设计原则的落点。
